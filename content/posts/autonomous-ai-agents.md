过去两年，我们习惯把大模型当成一个"更聪明的输入框"：你给它一段提示，它还你一段文本。Agent 改变了这个模型——它不再只是生成，而是**行动**。

## 一个 Agent 到底由什么组成

抛开营销词汇，能跑起来的 Agent 只有四个部件：

- **目标**：一个可以判断"做完了没有"的验收条件
- **工具**：读文件、跑命令、查网页、调 API 的能力
- **循环**：观察 → 决策 → 执行 → 再观察
- **记忆**：跨步骤保留的上下文，通常是一个不断增长的对话历史

最容易被忽略的是第一条。没有明确验收条件的 Agent，会陷入无限自我修正——它不知道什么时候该停。

## 工具设计比提示词重要

我见过太多团队在提示词上雕花，却把工具设计得很糟糕。事实上，模型能做什么，取决于你给它的工具粒度。

```js
// 差：粒度过粗，模型无法组合
const tools = { doStuff: async (input) => { /* 200 行 */ } };

// 好：小而正交，每个工具只做一件事
const tools = {
  readFile: async ({ path }) => fs.readFile(path, 'utf8'),
  listDir: async ({ path }) => fs.readdir(path),
  search: async ({ pattern, glob }) => ripgrep(pattern, glob),
  writeFile: async ({ path, content }) => fs.writeFile(path, content),
};
```

工具的描述文字同样是接口的一部分。写清楚"什么时候该用、参数是什么、失败会返回什么"，效果远好于在系统提示里加十句"请仔细思考"。

## 真实的落地场景

不是所有任务都值得用 Agent。目前真正跑得通的是这三类：

1. **信息收集与整理**——跨多个来源抓取、去重、结构化
2. **大范围但低风险的代码修改**——重命名、批量迁移、补测试
3. **验证闭环明确的流程**——改完能跑测试、能看截图、能对比输出

反过来，凡是"结果好坏无法自动判断"的任务，比如架构决策、产品设计，Agent 目前只能做草稿，不能做结论。

## 三个必须提前想清楚的问题

**成本上限。** 一个陷入循环的 Agent 可以在几分钟内烧掉几十美元。设置硬性的步数与 token 上限，比事后优化便宜得多。

**副作用。** 一旦 Agent 能写文件、发请求、改数据库，回滚策略就必须先于功能存在。我的习惯是：所有写操作先写到临时目录，验证通过后再原子替换。

**可观测性。** 你需要的不是"最后答案"，而是完整的执行轨迹。每一步的输入、输出、耗时都要能回看，否则出了问题只能靠猜。

## 一个朴素的判断

Agent 不会取代工程师，但会重新分配注意力。写样板代码的时间在减少，定义问题、设计验收标准、审查输出的时间在增加。

这其实是好事。那些本来就更像工程、而不像打字的部分，终于变成了工作的主体。
